## Summary

The project aim is demonstrated at four levels, each answering a different question:

| Level | Question | Objective | Method | When |
|---|---|---|---|---|
| **A. Software verification** | Does the system do what the requirements say? | O2 | Unit, API, UI and acceptance tests for every Must requirement, run in CI | Nov 2026 – Jan 2027 |
| **B. Rule-base verification** | Are the recommendations traceable and safe for every kind of user? | O1, O2 (SQ1) | Rule inspection; batch verification of plans for 200 synthetic profiles against hard constraints | Nov – Dec 2026 |
| **C. Usability evaluation** | Can people use the application without help? | O2, O3 | Moderated task-based test with at least 5 users; System Usability Scale (SUS) | Jan 2027 |
| **D. Pilot evaluation** | Does the system improve engagement and weight-related outcomes compared with self-monitoring alone? | O3, O4 (H1–H3) | 12-week, two-arm randomized controlled pilot, planned n = 60 | Feb – Apr 2027 |

Levels A–C are *verification* (the product is built correctly and is safe to give to participants); level D is *evaluation* (the product achieves its purpose). The pilot does not start until the go/no-go criteria of Section 7 are met.

Numbers in this plan come from the proposal or the requirements unless they are marked **(T)**. **(T)** marks a team-set value: a design choice made by the team for this plan, not a finding from data or literature. Every (T) value can be changed by the team or the supervisor before the plan is frozen (Section 6.10).

## 1. Purpose and Scope

### 1.1 Purpose

This plan defines, before any data are collected, how the project will show that its aim has been achieved: for every objective, which metric is measured, under which conditions, against which baseline, and what counts as success. Defining engagement and outcome measures in advance responds to a gap in the literature: among 59 studies of nutrition apps, only 31% defined engagement explicitly and 29% measured retention [3]. Evaluating the recommender only with algorithm metrics would repeat another limitation of the field (literature review, L5) [21]; the plan therefore combines technical verification with a controlled study with users.

### 1.2 What is being evaluated

| Element | Source |
|---|---|
| **Primary research question.** To what extent does a stand-alone mobile recommender system that jointly personalizes nutrition and physical activity recommendations through transparent, guideline-constrained rules improve 12-week engagement and weight-related outcomes in adults with overweight or class I obesity, compared with a self-monitoring-only version of the same application? | Proposal, Section 4 |
| **SQ1.** Do the recommendations generated by the rule engine satisfy predefined nutritional and physical activity constraints across representative user profiles? | Proposal, Section 4 |
| **H1 (O3).** The recommender-system arm will have a higher proportion of active days over the 84-day period than the control arm. | Proposal, Section 5 |
| **H2 (O4).** The recommender-system arm will achieve a greater mean percentage reduction in body weight at week 12. | Proposal, Section 5 |
| **H3 (O4).** The recommender-system arm will show a greater increase in mean daily steps from baseline to weeks 11–12. | Proposal, Section 5 |

All hypothesis tests are two-sided with α = 0.05 (proposal, Section 5).

### 1.3 Baseline (comparator)

The baseline for the pilot is the **same application in self-monitoring-only mode** (FR-31): participants log food, weight and steps, see their progress and answer the weekly check-in, but receive no factor ranking, recommendations, explanations or activity prompts. This active, same-app comparator is chosen because wait-list controls inflate the effects of digital interventions, and active controls produced no significant effect in a meta-analysis of 19 RCTs [1]; because tailored feedback did not beat self-monitoring alone in the 12-month SMARTER trial [2]; and because both arms then share the same interface, food database and logging effort, so that the difference between arms isolates the recommender functions (literature review, L1, L2, G4).

For rule-base verification (level B), the baseline is the set of hard constraints themselves: a plan either satisfies every constraint or it does not. For usability (level C), the benchmark is a mean SUS score of 68, the average in published benchmark data [11], [12] (NFR-17).

## 3. Level A: Software Verification

### 3.1 Approach

Testing follows the general concepts of ISO/IEC/IEEE 29119-1 [20]: test levels, a test basis (the requirements specification v1.3), test cases with expected results, and exit criteria. Mobile security checks follow the OWASP MASVS controls named in the requirements and the test procedures of the OWASP Mobile Application Security Testing Guide (MASTG) [18], [19]. All testing in this phase uses synthetic or test data in the development environment; no participant data exist before ethics approval (CON-04, NFR-06).

### 3.2 Test levels

| Level | Scope | Tools (planned) | Run |
|---|---|---|---|
| **Unit** | Rule evaluator, each rule, factor scoring, constraint checker, data validation (backend); view models and formatting (client) | `pytest` (Python), `flutter_test` (Dart) | Every pull request (NFR-26) |
| **API / integration** | Each REST endpoint against a test PostgreSQL database: authentication, role-based access (NFR-05), logging, weekly update job, randomization, export (FR-35) | `pytest` with the FastAPI test client | Every pull request |
| **UI (widget)** | Screens and navigation in both application modes, three languages (FR-39, NFR-19), explanation screen (FR-23) | `flutter_test` widget tests | Every pull request |
| **End-to-end** | Core scenarios on real devices: register, consent, screen, log food, view recommendation and explanation; control-mode scenario | Flutter `integration_test`; manual demonstration on the minimum-version Android and iOS devices (NFR-20) | Before each release candidate |
| **Non-functional** | Response time and load (NFR-09–NFR-11), offline sync (NFR-12), notification delay (NFR-15), TLS and storage checks (NFR-01, NFR-02), secret scan (NFR-08), backup restore (NFR-13) | Load-testing script (e.g. Locust), TLS scanner, repository secret scanning, manual checks per MASTG | Before the go/no-go review (Section 7) |

Should and Could requirements are tested in the same way; a failed Should requirement does not block the pilot if a workaround is documented (requirements, Section 2.2).

### 3.4 Defects and exit criteria

Defects are recorded in YouTrack (project DOA) with a severity: **critical** (data loss, wrong eligibility decision, a recommendation that violates a hard constraint, a privacy breach, a crash in a core scenario), **major** (a requirement not met, no safe workaround) or **minor** (cosmetic or with a workaround) **(T)**.

Exit criteria for level A: all 48 Must acceptance tests pass on the release candidate; no open critical or major defect; CI is green on the release commit.

## 4. Level B: Rule-Base Verification (O1, SQ1)

Rule-base verification is planned in detail here and carried out in DOA-23. The numeric targets and limits of the rules (energy ranges, macronutrient shares, calcium threshold, step increments, intensity zones) are defined and sourced in the rule base (DOA-16), mainly from the EASO position statement on medical nutrition therapy [6] and the exercise evidence cited there; this plan fixes how they are checked, not their values.

### 4.1 Verification activities

| ID | Activity | Requirement | Pass criterion |
|---|---|---|---|
| **V1** | **Rule inspection.** Each rule is checked for inputs, output, constraint, evidence source and version, and the evidence source is checked against the reference list. | FR-37, O1 | 100% of rules complete and each source verifiable |
| **V2** | **Rule unit tests.** At least one typical and one boundary case per rule, run in CI. | NFR-26 | 100% of rules covered; all tests pass |
| **V3** | **Batch verification on 200 synthetic profiles** (SQ1, Section 4.2). | FR-38, NFR-24, FR-23 | 0 violations of HC1–HC4; 100% of recommendations explained |
| **V4** | **Determinism and reproducibility.** V3 is run twice on the same profiles and rule version and the reports are compared by hash; 20 randomly sampled stored recommendations are re-computed from their stored inputs and rule version. | NFR-22, NFR-23 | Identical reports; 20 of 20 reproduced |
| **V5** | **Fault injection.** Plans with deliberately injected violations (one per constraint and per boundary direction) are passed to the system. | FR-24 | Every injected violation is detected, not shown, replaced by a fallback and logged |
| **V6** | **AI food-logging check** on the local-food test list (Section 4.4). | FR-40, NFR-25 | See Section 4.4 |

### 4.2 Synthetic profiles

**Generation.** A generator in `ml/` (DOA-23) produces 200 profiles inside the eligible population (proposal, Section 3): age 18–60 years, both sexes, BMI 25.0–34.9 kg/m², and each self-reported activity level defined in the onboarding questionnaire. Height ranges used to derive weight from BMI are set in DOA-16. The set has two parts:

1. **Boundary profiles.** Every combination of the boundary values age {18, 60}, BMI {25.0, 29.9, 30.0, 34.9}, sex and activity level. With *k* activity levels this gives 16*k* profiles (for example, 48 with three levels).
2. **Stratified random profiles.** The remaining profiles are drawn by stratified random sampling across age bands, BMI class and activity level, so that every combination is represented, using a fixed random seed recorded in the report.

**Simulated follow-up (T).** Because energy and step targets are updated weekly from logs (FR-15, FR-18), each profile is also run through 12 simulated weeks under scripted trajectories: stable weight, weight loss, weight gain, low logging and missing weeks. Every weekly plan is checked against the same constraints. This extends SQ1 from initial plans to the plans that participants will actually receive over the pilot.

### 4.3 Hard constraints and additional checks

| ID | Hard constraint (proposal, O2; requirements, Section 1.4) | Check |
|---|---|---|
| **HC1** | Energy target within the target range defined for the profile | Computed energy of the plan lies within [lower, upper] of the rule |
| **HC2** | Macronutrient shares within guideline ranges [6] | Protein, fat and carbohydrate shares of energy each within their range |
| **HC3** | Calcium adequacy | Calcium of the plan at or above the rule threshold |
| **HC4** | Activity intensity not above the profile's current zone | Recommended intensity or heart-rate zone ≤ current zone (FR-19) |

Additional checks in the same run: no step target below the baseline and no weekly increase above the rule step (FR-18); exactly two resistance sessions on non-consecutive days (FR-20); at most three prompts per day and none outside active hours in a simulated 14-day log (FR-25); recommendations ordered by the highest-ranked deviating factor (FR-22); no recommendation, factor ranking or prompt for ineligible or control-arm accounts (FR-05, FR-31).

**Independent checker.** The constraint checker is written from the requirement text as a separate module and does not import the rule-engine code that it checks, so that one programming error cannot appear in both and hide itself.

**Output.** `verification-report.md` lists, per profile and week, the plan, each constraint result (pass or fail with value), the rule version, the random seed and the commit hash. Every failure, the rule change made and the re-run result are kept in the report (DOA-23 acceptance criteria).

### 4.4 AI-assisted food logging (FR-40)

AI output does not enter the recommendation path (NFR-25), so it is not part of SQ1. Its accuracy is measured separately because wrong food matches would distort logged intake, especially for local dishes (technology comparison, R5). Generative models can give nutritionally wrong output [5], which is why the user confirms every suggestion.

| Metric | Definition | Criterion |
|---|---|---|
| Identification accuracy | Share of test meals for which the correct database food is among the top 3 suggestions, separately for text and photo input | Proposed ≥ 80% **(T)**, to be confirmed by the team |
| Database containment | Share of suggestions that are foods from the project database | 100% (FR-40) |
| Request privacy | Logged requests to the AI service contain no user identifier or profile data | 100% by inspection (FR-40) |

The test set is the local-food test list compiled in DOA-16. If the accuracy criterion is not met, or if the ethics review does not allow the feature (Section 8.4), FR-40 is switched off for the pilot in both arms.

## 6. Level D: Pilot Evaluation (O3, O4)

The pilot is reported following the CONSORT 2025 statement [8] and its extension for randomized pilot and feasibility trials [7].

### 6.1 Design

A 12-week, two-arm, parallel-group randomized controlled pilot study with 1:1 allocation, conducted in Astana from February to April 2027 (proposal, Section 10; DOA-25).

| Arm | Application mode | Functions |
|---|---|---|
| **Intervention (IA)** | Full recommender system | Logging, progress, check-ins, factor identification and ranking, weekly targets, recommendations with explanations, activity prompts, sitting-break prompts |
| **Control (CA)** | Self-monitoring only (FR-31) | Logging, progress (without targets), check-ins |

Both arms use the same application build, food database, logging functions, weekly check-in and study reminders for measurement visits. Neither arm receives human coaching, so that coaching does not confound the effect of the application (literature review, L7). AI-assisted food logging (FR-40) is either available in both arms or in neither (technology comparison, D7), so that it does not confound the comparison; its use is recorded per arm.

### 6.2 Participants

**Inclusion:** age 18–60 years; BMI 25.0–34.9 kg/m² measured at the baseline visit; own Android (9 or later) or iOS (15 or later) smartphone (NFR-20); able to walk for 10 minutes; written informed consent.

**Exclusion:** diagnosed diabetes or cardiovascular disease; pregnancy; current weight-loss medication; contraindications on the PAR-Q+ [13]; participation in the usability test.

**Recruitment:** the AITU community and the wider Astana population through university channels, posters and social media (proposal, Sections 3, 9), only after ethics approval.

### 6.3 Sample size

The planned sample is 60 participants, 30 per arm (proposal, Section 6). With 30 per arm, a two-sided two-sample t-test at α = 0.05 has 80% power only for a standardized difference of about d = 0.74 (computed with statsmodels [15]). The study is therefore a pilot: it estimates effects and their variability, and it measures feasibility, to size a later confirmatory trial [7]. Feasibility outcomes are:

| Feasibility outcome | Definition |
|---|---|
| Recruitment rate | Participants randomized per week of recruitment |
| Eligibility and consent | Screened → eligible → consented → randomized (CONSORT flow diagram [7]) |
| Retention | Share of randomized participants who complete the week-12 visit |
| Data completeness | Share of participant-days with step data; share of weekly check-ins answered; share of scheduled measurements obtained |

### 6.4 Randomization and blinding

**Sequence generation.** Computer-generated, permuted blocks of randomly varying size (2 and 4), stratified by sex and BMI class (25.0–29.9 and 30.0–34.9 kg/m²) **(T)**. Stratification keeps the arms balanced on two variables that affect weight change, which matters in a small sample.

**Allocation concealment.** The sequence is generated with a recorded seed by a team member who does not enroll participants and is stored in the backend. The arm is assigned automatically only after the participant's consent and baseline measurements are saved (FR-30), and no participant-facing or RA screen shows the next allocation.

**Blinding.** Participants are told that two versions of the application are compared, without being told which version is expected to work better; the exact wording is approved by the ethics committee. The RA who measures weight and waist cannot be fully blinded in a three-person team; this is mitigated by the standardized measurement protocol (Section 6.6) and reported as a limitation. The primary analyses are run on data with arm labels masked as A and B; the labels are revealed after the analysis results are recorded.

### 6.5 Study timeline per participant

| Time | Procedures |
|---|---|
| **Screening** | Online eligibility screening in the app (FR-04, FR-05), including PAR-Q+ [13] |
| **Week 0 visit** | Information and written consent; height, weight and waist measured by the RA; installation and onboarding; randomization (FR-30) |
| **Days 1–7 (baseline week)** | Both arms log; steps collected; no targets or prompts in either arm (FR-12). Provides the step baseline for H3 and the prompt thresholds |
| **Day 8 – day 84** | IA receives targets, recommendations and prompts; CA continues self-monitoring. Weekly adverse-event check-in in both arms (FR-28) |
| **Week 6 visit** (±7 days **(T)**) | Weight and waist measured by the RA |
| **Week 12 visit** (±7 days **(T)**) | Weight and waist measured by the RA; SUS (FR-33); visit completion recorded (retention) |

Day 1 is the first full day after the week-0 visit. The 84-day period is days 1–84.

### 6.6 Measurement protocol

| Measure | Protocol |
|---|---|
| **Weight** | Same calibrated digital scale for all visits, light clothing, no shoes, recorded to 0.1 kg; where possible at the same time of day as the baseline visit **(T)** |
| **Height** | Stadiometer, no shoes, at week 0 only, to 0.1 cm |
| **Waist circumference** | WHO protocol [14]: at the midpoint between the lower margin of the last palpable rib and the top of the iliac crest, at the end of a normal expiration, with a stretch-resistant tape; two measurements, averaged if they differ by no more than 1 cm, otherwise repeated |
| **Steps** | Daily step count from the phone or, if connected, the wearable (FR-10, FR-11). The source used in the baseline week is used for the whole study for that participant, so that a change of device does not create a change in steps; the source is recorded |
| **Engagement events** | Time-stamped app events with time-zone offset (FR-32, NFR-16) |
| **Adverse events** | Weekly in-app check-in (FR-28); reports trigger the procedure in Section 8.3 |

Each RA measurement is stored with the week, date and source flag (FR-34). Self-reported in-app weights are kept separately and are not used for H2 except in a sensitivity analysis.

### 6.7 Outcome definitions

| Outcome | Operational definition |
|---|---|
| **Active day** (H1) | A calendar day, in the participant's local time zone, with at least one user-initiated logging event: a food entry (manual or AI-assisted and confirmed), a weight entry or a waist entry. App opens, step synchronization and recommendation views do not count, because they are either passive or available in only one arm |
| **Proportion of active days** (H1, primary engagement outcome) | Number of active days in days 1–84 divided by 84. Days after withdrawal count as inactive |
| **Retention** | Week-12 visit completed within its window |
| **Prompt response** (IA only) | A prompt is counted as responded to when the steps recorded in the 60 minutes after it exceed the participant's mean hourly steps during active hours in the baseline week **(T)**. Also reported: share of prompts opened (FR-32). Requires step data with at least hourly resolution (see note below) |
| **SUS** | Standard 0–100 score at week 12 [10] |
| **Percentage weight change** (H2) | (week-12 weight − week-0 weight) / week-0 weight × 100, RA-measured |
| **Change in daily steps** (H3) | Mean daily steps over valid days of weeks 11–12 minus mean daily steps over valid days of the baseline week. A valid day has step data from the participant's step source; at least 4 valid days are needed in each period **(T)** |
| **Waist change** | Week-12 minus week-0 waist circumference, cm |
| **Adverse event** | Any injury, pain, dizziness or other health problem reported in a check-in or to the team. **Serious** if it leads to hospital care or prevents daily activities **(T)**; final definitions follow the ethics application (DOA-24) |

**Note on step resolution.** FR-10 currently requires a daily step count. The prompt-response outcome needs step counts with at least hourly resolution around each prompt. The plan therefore proposes amending FR-10 (requirements v1.4) to store step counts per hour (or finer, where the platform provides them).

### 6.8 Statistical analysis

All analyses use Python with pandas and statsmodels [15]. The analysis scripts are written and tested on simulated data in `ml/` before the first participant is enrolled.

**Analysis population.** Intention to treat: every randomized participant is analysed in the arm to which they were allocated. A per-protocol analysis (participants with the week-12 visit and at least one logging event in each of weeks 2–12 **(T)**) is reported as a sensitivity analysis.

| Outcome | Primary analysis | Sensitivity analysis |
|---|---|---|
| **H1** proportion of active days | Binomial generalized linear model (logit link) of active days out of 84, with arm and the stratification variables (sex, BMI class) as covariates and the scale estimated from the data to allow for over-dispersion; reported as the adjusted difference in mean proportion with 95% CI (bootstrap) and the odds ratio | Mann–Whitney U test on the proportion; per-protocol |
| **H2** percentage weight change | Analysis of covariance (ANCOVA): week-12 percentage change on arm, adjusted for baseline weight and stratification variables [9]; mean difference with 95% CI | Complete cases; week-12 self-reported weight where the RA measurement is missing |
| **H3** change in daily steps | ANCOVA: mean daily steps in weeks 11–12 on arm, adjusted for baseline-week mean steps and stratification variables [9] | Complete cases; adjustment for wearable use |
| Waist change | ANCOVA as for H2 | Complete cases |
| Retention | Risk difference with 95% CI; Fisher's exact test | — |
| SUS | Mean (SD) per arm; Welch t-test; share of participants with SUS ≥ 68 | — |
| Prompt response | Descriptive: share of prompts responded to per week, to show whether response fades over time (literature review, L9) [4], [22] | — |
| Adverse events | Number of participants with events and number of events per arm, by type and seriousness; no hypothesis test | — |

ANCOVA is preferred to comparing change scores because it adjusts for chance baseline imbalance and generally has more statistical power [9].

**Missing data.** The amount and pattern of missing data are reported per arm. For H2 and H3, missing week-12 values are handled by multiple imputation by chained equations (statsmodels MICE) with arm, stratification variables, baseline value and week-6 value (for H2) as predictors, 20 imputations **(T)**; the complete-case analysis is reported alongside.

**Multiplicity.** H1–H3 are each tested at α = 0.05, two-sided, as specified in the proposal. Because the study is a pilot, no confirmatory claim is made; Holm-adjusted p-values are reported in addition, and the interpretation is based on effect estimates and confidence intervals [7].

**Estimates for a future trial.** The standard deviation of each outcome and the standardized effect with its 95% CI are reported for use in sample-size calculation of a confirmatory trial.

### 6.9 Data management

Pseudonymized exports (FR-35) in CSV with a data dictionary (NFR-27) are the only input to the analysis. Participant data are stored only on the server in Kazakhstan (NFR-06) and never in the repository (NFR-08); the analysis scripts in the repository read data from a local path outside it. Backups and restore are tested before enrollment (NFR-13).

### 6.10 Freezing the plan

Before the first enrollment, this plan and the analysis scripts are frozen as a tagged version in the repository. Any later change is recorded in the version history with its reason and date, and changes made after unmasking the arm labels are reported as post-hoc. ## 8. Ethics and Data Protection

The pilot and the usability test involve human participants and health data. They are carried out under AITU ethics approval (DOA-24) and in line with the ethical principles of the WMA Declaration of Helsinki [16]. This section lists what the ethics application must cover; the application itself is prepared in DOA-24.

### 8.1 Approval and consent

- No participant data are collected before ethics approval and written informed consent (CON-04). This applies to the usability test as well as to the pilot.
- The information sheet explains: the purpose; that two versions of the application are compared and allocation is random; what data are collected and why; where data are stored; the use of an external AI service, if approved (Section 8.4); risks; the right to withdraw at any time without giving a reason (FR-03); and contact details.
- Consent is recorded on paper or electronically and in the application with its version and timestamp (FR-02).

### 8.2 Safety screening and referral

- Eligibility and PAR-Q+ screening [13] are applied before enrollment; ineligible people are referred to clinical care and receive no recommendations (FR-04, FR-05).
- The application is a lifestyle-support tool. It does not diagnose, prescribe medication or change medical treatment (proposal, Section 7.2), and the information sheet says so.

### 8.3 Adverse events

- Every participant answers a weekly check-in (FR-28). A reported adverse event suspends activity recommendations and prompts for that account, shows advice to seek medical care, and alerts the RA (FR-29).
- The team contacts the participant, records the event, its seriousness and its possible relation to a recommendation, and informs the supervisor. Serious events are reported to the ethics committee within the time it sets.
- **Stopping rule (T).** Enrollment and recommendations are paused for review by the supervisor if a serious adverse event is judged possibly related to a recommendation.

### 8.4 AI-assisted food logging and external data transfer

Sending meal descriptions or photos to an external AI service (FR-40) is a separate ethics and legal question, because:

- the provider's servers are likely to be outside Kazakhstan, so the transfer may count as cross-border transfer of personal data under the Law on Personal Data and Their Protection [17], while NFR-06 requires participant data to be stored in Kazakhstan;
- a photo can contain more than food: faces, other people, documents, and location or device metadata.

**Safeguards proposed for the ethics application:**

1. The request contains no user identifier and no profile data (FR-40); this is checked by inspection of logged requests.
2. The client removes image metadata (EXIF, including location) and reduces the image size before sending; participants are asked to photograph only the plate.
3. A provider is chosen whose terms allow the team to opt out of data retention and model training, where such an option exists; the terms are recorded at selection.
4. A separate, optional consent item for AI-assisted logging; manual logging is always available.
5. The RA can switch the feature off for all users at any time (FR-40).

**Decision rule.** If the ethics committee and the legal check approve the feature with these safeguards, it is offered in both arms with separate consent and its use is reported per arm. If not, FR-40 is switched off for the whole pilot. In neither case does the feature differ between arms.

### 8.5 Data protection

- Pseudonymous study ID for all research data; direct identifiers stored separately and never exported (NFR-03).
- Data minimization: only data in the data dictionary are collected (NFR-04).
- Encryption in transit and at rest (NFR-01, NFR-02); role-based access (NFR-05).
- Storage on a server in Kazakhstan (NFR-06); retention period and deletion procedure as approved in DOA-24 (NFR-07).
- No personal data in the repository, reports or thesis; results are reported only in aggregate.

### 8.6 Fairness to the control arm and conflict of interest

- Control participants receive an application that is useful on its own (self-monitoring). The team proposes to offer them the full version after their week-12 visit **(T)**, subject to ethics approval.
- The developers of the system also evaluate it. This is mitigated by pre-specifying the plan and analysis (Section 6.10), masking arm labels during analysis, and reporting all outcomes, including null and negative results.

## 9. Threats to Validity

| Type | Threat | Mitigation |
|---|---|---|
| Internal | Participants cannot be blinded to the functions they see | Neutral description of the two versions (Section 6.4); objective outcomes (measured weight, steps) |
| Internal | The RA who measures outcomes is not blinded | Standardized protocol and calibrated scale (Section 6.6); masked analysis |
| Internal | Contamination: participants from the same university may share information or the application | Participants are asked not to share study details; arm-level differences are interpreted with this in mind |
| Internal | Missing outcome data and drop-out | Study reminders, visit windows, multiple imputation with complete-case comparison |
| Construct | Active days measure logging, not eating or activity behaviour | Weight, waist and steps are measured separately (O4) |
| Construct | Self-reported food intake is inaccurate | Food logs are used for targets and engagement, not as an outcome |
| Construct | Phone and wearable step counts differ | One step source per participant for the whole study; wearable use recorded |
| Construct | SUS translations not formally validated | Forward–backward translation; language recorded per response |
| Statistical | Small sample: only large effects (d ≈ 0.74) detectable at 80% power | Pilot framing; effect estimates and CIs; no confirmatory claim |
| External | University-based sample in one city; 12-week duration | Population described in detail; long-term maintenance out of scope (literature review, L8) |
| External | Novelty effect in the first weeks | Weekly engagement trajectories reported, not only the 84-day total |
