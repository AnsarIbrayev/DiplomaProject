## 1. Introduction

### 1.1 Purpose

This document specifies the functional requirements (FR) and non-functional requirements (NFR) of the proposed system. Every requirement has an identifier, a priority, a source and an acceptance criterion, so that it can be traced to the project objectives and verified. The document is the basis for the architecture (DOA-9), the use case diagram (DOA-10), the prototype (DOA-11) and the verification and evaluation plan (DOA-12).

### 1.2 Scope

The system is a cross-platform mobile application with a backend that (a) screens adults with overweight or class I obesity for eligibility, (b) collects dietary, weight and activity data, (c) identifies each user's modifiable lifestyle factors that deviate most from guideline-based targets, and (d) gives joint nutrition and physical activity recommendations generated by transparent, versioned rules, each with an explanation. The same application runs in a self-monitoring-only mode for the control arm of a 12-week randomized pilot. The boundaries of the scope follow the proposal (Section 7); out-of-scope items, such as medical diagnosis, human coaching and opaque generative models, are not repeated here.

### 1.3 Users and roles

| Role | Description | Source |
|---|---|---|
| **Participant, intervention arm (IA)** | Eligible adult (18–60 years, BMI 25.0–34.9 kg/m², no exclusion condition) who receives factor identification, recommendations and prompts | Proposal, Sections 3, 7.1 |
| **Participant, control arm (CA)** | Eligible adult who uses the same application for tracking only: no factor ranking, recommendations or prompts | Proposal, Section 7.1; literature review, L1 |
| **Ineligible user** | Person who fails screening; receives a referral to clinical care and no recommendations | Proposal, Section 3 |
| **Research administrator (RA)** | Team member who manages enrollment, records study measurements and exports pseudonymized data | Proposal, Section 3 |
| **Rule maintainer** | Team member who edits, versions and verifies the rule base | Proposal, Section 8 |

"User" in this document means any participant (IA or CA) unless a requirement names a role.

### 1.4 Definitions

| Term | Meaning in this document |
|---|---|
| Rule base | The set of documented, versioned rules that convert user data into factor scores and recommendations (O1, DOA-16) |
| Hard constraint | A condition every generated plan must satisfy: energy within the target range, macronutrient shares within guideline ranges, calcium adequacy, activity intensity not above the profile's current zone (proposal, O2) |
| Baseline week | The first 7 days after onboarding, during which data are collected and no step target or prompt is given; used to derive personal thresholds (proposal, Section 7.1) |
| Deviating factor | A modifiable lifestyle factor (proposal, Section 2.3) whose value differs from its guideline-based target |
| Active day | A calendar day, in the user's local time zone, with at least one food, weight or waist log entry; app opens, step synchronization and recommendation views do not count (evaluation plan, Section 6.7) |

## 2. Conventions

### 2.1 Identifiers

`FR-xx` functional requirement; `NFR-xx` non-functional requirement; `CON-xx` project constraint. Identifiers are never reused; a deleted requirement keeps its ID with the status "withdrawn".

### 2.2 Priority (MoSCoW)

| Priority | Meaning for this project |
|---|---|
| **Must** | Required for the 12-week pilot or for answering SQ1; the pilot cannot start without it |
| **Should** | Important; planned for the pilot prototype, but the pilot can run without it with a documented workaround |
| **Could** | Desirable; implemented only if time allows |
| **Won't (this release)** | Agreed as out of scope for the diploma (see proposal, Section 7.2) |

### 2.3 Source status

Each requirement states where it comes from and how strong that basis is. This distinguishes verified findings from assumptions, as required by the pre-defense criteria.

| Code | Status | Meaning |
|---|---|---|
| **E** | Evidence | Based on a cited study, guideline or desk-research finding (literature review L1–L16, existing-system gaps G1–G4, desk findings D1–D6) |
| **P** | Project decision | Fixed in the project proposal (aim, objectives O1–O4, scope, eligibility) |
| **R** | Regulation or standard | Required by law or an external standard (references [1]–[6]) |
| **A** | Assumption | Depends on a user or expert assumption (A1–A12, E1–E4) that is **unverified** until the interviews of DOA-4 are analysed |
| **T** | Team-set target | A numeric threshold chosen by the team as an engineering target; not derived from evidence, and reviewed after verification |

### 2.4 Acceptance criteria and verification methods

Acceptance criteria are written as Given/When/Then statements or as a measurable threshold. Every **Must** requirement has a testable criterion. The verification method is one of: **T** test (automated or manual), **D** demonstration on a device, **I** inspection of code, configuration or documents, **An** analysis of logs or data.

## 7. Open Questions

1. **Interface languages (resolved, 22 October 2026).** The team decided that Kazakh, Russian and English are equal Must languages with an in-app switch (FR-39, NFR-19). The existing-system comparison found Kazakh only in TayQazan Tracker (G3). Translations of rule explanations need a review by a native speaker of each language before the pilot.
2. **AI component (resolved, 22 October 2026).** The team chose AI-assisted food logging only (FR-40); recommendations remain rule-based (NFR-25). Open: whether sending participants' meal photos or text to an external AI service is allowed by the ethics approval and by the Law on Personal Data (cross-border transfer); to be confirmed in DOA-24. If it is not allowed, FR-40 is switched off for the pilot.
3. **Data residency (NFR-06).** Applicability of Article 12(2) of the Law on Personal Data to a university research prototype is to be confirmed with the supervisor and the ethics committee.
4. **Team-set thresholds** (prompt limit, response times, availability, notification delay). They are engineering targets and may be adjusted after the prototype is measured; any change is recorded in this document's version history.
